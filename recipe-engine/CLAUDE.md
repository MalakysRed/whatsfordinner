# Recipe Engine

Authored data layer for WhatsForDinner. Generates recipes from hand authored
techniques, dish archetypes and an ingredient ontology, rather than asking a
model to invent them.

Repo level conventions live in the root `CLAUDE.md` and still apply. This file
covers only what is specific to `/recipe-engine`.

## Status

Standalone. Nothing here is imported by the app yet. Safe to break, safe to
delete. Do not modify anything outside `/recipe-engine` without asking.

## Architecture in one paragraph

Dish archetypes define an ordered sequence of steps with fillable ingredient
slots. Techniques define what each step does, how long it takes and how to tell
it has worked. The constraint layer sets quantities. A recipe is generated by
choosing an archetype, filling its slots, and computing everything else. The
model writes prose only.

`SPEC.md` is the schema authority. Follow it exactly. Ask before deviating.

## Hard rules

**Never invent culinary content.** Sensory cues, failure modes, `impact_note`
text, suitability scores and quantity rules are authored by me. You may draft
them when I explicitly ask, but mark the record `status: draft` and tell me
which fields you drafted. Plausible-but-unverified culinary claims are the
exact failure mode this whole architecture exists to prevent.

**The model never sets numbers.** In `generate.ts`, all quantities come from
the constraint layer and all durations from technique `duration_model` values.
Model output is validated against authored records; unknown IDs are rejected,
never corrected.

**Zod schemas in `/schemas` are the single source of truth for record shape.**
Types come from `z.infer`. Never hand write a type that duplicates a schema.

**Data records are TypeScript**, declared with `satisfies` against the inferred
type so errors surface in the editor while authoring.

## Conventions

- Metric only: grams, millilitres, tbsp = 15ml, tsp = 5ml. Never cups.
- UK English spelling throughout, including in authored prose fields.
- IDs are uppercase with a type prefix and are permanent once created:
  `TECH_`, `PAT_`, `ARCH_`, `ING_`, `SLOT_`, `OPT_`, `RULE_`.
  Never renumber or reuse an ID.
- One record per file, filename matching the slug.
- Every authored record carries `status`: `draft` | `review` | `published`.
- Archetypes carry `verification_status`: `unverified` until I have cooked it.

## Authoring order

Top down, always. An archetype is written first; it reveals which techniques,
patterns and ingredients are actually needed. Do not generate speculative
technique or ingredient records that no archetype references.

## Layout

```
/data
  /techniques/*.ts     one technique per file
  /archetypes/*.ts     archetype, its steps, slots and slot options
  /ingredients/*.ts    canonical ingredients
  /constraints/*.ts    quantity and seasoning rules
  index.ts             barrel export
/schemas               Zod 4 schemas + inferred types
/lib
  validate.ts          referential and step sequencing checks
  generate.ts          archetype + slot fills -> recipe
/tests
  data.test.ts         runs validate over all authored data
SPEC.md                schema authority
```

## Validation

`validate.ts` must check, at minimum:

- every referenced ID resolves
- required slots are filled and cardinality is respected
- no conflicting slot options are co-selected
- each step's `produces` satisfies the next step's `accepts`
- every quantity traces to a `quantity_rule_id`
- computed totals are consistent with the sum of step durations

Run via Vitest. Data validity is a test failure, not a warning.

## Ask before

- deviating from `SPEC.md`
- adding a dependency
- touching anything outside `/recipe-engine`
- writing to Supabase or creating a migration
